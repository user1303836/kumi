# オーディオインテリジェンス

[English](../en/AUDIO_INTELLIGENCE.md) · [简体中文](../zh-CN/AUDIO_INTELLIGENCE.md) · 日本語

MCP クライアント向けの、ブリッジのオーディオツールです。送られたオーディオを測定し、リファレンスと比較し、測定結果を Live のトラックと関連付け、Live から短いキャプチャを録音して測定したあと削除します。

**Kumi はこれらのツールを使いません。** Kumi には、あなたのコンピューター上で動く独自の聴く機能があります。オーディオファイルと Set のオーディオクリップを読み取り、自分が作ったものを録音またはレンダリングし（`audition` ツールは、Kumi Ears デバイスを通じて Live の中で各候補を聴き、Max for Live がなければ候補ごとにスクラッチトラックに録音します。その間も Main はあなたの設定のまま鳴ります。`render` は Kumi の Live 拡張機能を通じてオーディオトラックのクリップをレンダリングします）、その結果を測定します。Kumi ガイドの[聴く](KUMI_GUIDE.md#聴く)と、[Kumi が Set を変更するしくみ](KUMI_CHANGES.md)を参照してください。

## ツール

| ツール | 受け取るもの | 返すもの |
| --- | --- | --- |
| `audio_analyze` | base64 にした、−1…1 に正規化されたインターリーブのリトルエンディアン float32 PCM：8–384 kHz、1–32 チャンネル、最大 10,000,000 サンプルかつ 600 秒 | `pcm-analysis/v3`：ラウドネス、ピーク、スペクトル、ダイナミクス、トランジェント、クリッピング |
| `audio_compare_reference` | 同じ形式のソース 2 つ：32–96 kHz、モノラルまたはステレオ、それぞれ最大 30 秒、合わせて最大 4,000,000 サンプル | `reference-analysis/v2`：両方の解析、アライメント、差分 |
| `audio_diagnose_live_context` | `audio_analyze` と同じ形式のモノラルまたはステレオの PCM と、`trackRef` 1 つ | 解析結果と、トラック、そのデバイス、ルーティングに結び付けた所見 |
| `live_audio_capture_preview/apply`、`live_audio_capture_status`、`live_audio_capture_emergency_stop` | Session のクリップ 1 つ、空のオーディオスロット 1 つ、1–9 秒 | Live の Resampling 入力の解析。録音はそのあと削除されます |

どれもファイルパスや URL を受け付けず、オーディオを返すこともありません。送られた PCM が Live の出力として扱われることはありません。Live との結び付けには、ブリッジ自身が行ったキャプチャを除き、常に「あなたが保証するもの」という印が付きます。

## 測定

`pcm-analysis/v3` の `standardsAudio` は、公開されている規格に従います。

- ITU-R BS.1770-5 のプログラムラウドネス（EBU R128 の運用方法に沿う）
- EBU Tech 3341 のモーメンタリー（400 ms）とショートターム（3 s）のラウドネス
- EBU Tech 3342 のラウドネスレンジ：−70 LUFS の絶対ゲート、−20 LU の相対ゲート
- 100 ms ごとの 400 ms ブロックから求めるインテグレーテッドラウドネス。−70 LUFS と −10 LU でゲート
- チャンネルの重み：モノラルとステレオは推定し、それより大きいレイアウトには `M`、`L`、`R`、`C`、`Ls`、`Rs`、`LFE` のラベルが必要です。LFE は除外し、サラウンドの重みは 1.41
- サンプルピークとトゥルーピーク（別々に報告）

トゥルーピークは、48 kHz では BS.1770-5 Annex 2 の 4 フェーズ・48 次のフィルターを使い、44.1 kHz ではまず 64 タップの Blackman 窓付き sinc 変換で 48 kHz に変換します。ほかのレートでは、トゥルーピークは利用不可と報告されます。ラウドネスは 8 から 384 kHz までの任意の整数レートで動作し、48 kHz では公開されたフィルター係数を使います。

無音、短すぎるオーディオ、不明なマルチチャンネルレイアウト、トゥルーピークの処理量の上限を超える入力では、NaN や無限大やでっち上げの数値ではなく、明示的な利用不可の値を返します。モーメンタリーとショートタームの系列は最大 128 点ですが、ゲーティングにはすべてのウィンドウを使います。

`clipping` は、フルスケールに達したソースのサンプルを数えます。`reconstructedOvers` は、再構成したあとにだけ現れる 0 dBFS を超える値を数えるもので、ソースがクリップしていることの証明にはなりません。`loudness` フィールドは互換性のために残している古い RMS の推定値です。デリバリーやマスタリングの判断には `standardsAudio` を使ってください。

## リファレンスとの比較

`audio_compare_reference` は次のように動きます。

1. 各ソースを 32 タップの Blackman 窓付き sinc カーネルで 48 kHz に変換します。
2. 100 Hz での粗い探索のあと、±10 ms の範囲で 1 kHz での細かい探索を行って位置を合わせます（`alignment.mode` はデフォルトの `auto`、オフセットを指定する `manual`、または `disabled`）。`maxLagSeconds` はデフォルトが 5 で、最大 10 です。
3. 弱い、無音の、またはあいまいな自動一致は拒否します。その場合も各ソースは解析されますが、重なりはゼロになり、差分はすべて伏せられます。
4. そうでなければ重なった部分だけを解析し、インテグレーテッドラウドネスの差、±24 dB の範囲でのレベル合わせの提案、そしてトゥルーピークとサンプルピーク、RMS、クレスト、ダイナミックレンジ、スペクトル、トランジェント密度の差を報告します。

`resampling.*.sourceClipping` は、変換前の各ソースのフルスケールのサンプルを数えます。リサンプリングは時間を伸縮したりテンポを合わせたりせず、レベル合わせの提案はオーディオを変えません。位置を合わせたオーディオは返されません。

## 診断

`audio_diagnose_live_context` は、あなたの PCM を解析し、トラックの最新のスナップショット（Set、トラック、そのミキサーとルーティング、順番どおりのデバイスとそのパラメータ値）を 1 つ読み取り、測定結果をそれに結び付けます。この結び付けには「あなたが宣言したもので、未検証」という印が付きます。キャプチャのあとでは `verified-by-capture-lifecycle` という印が付きます。

所見では、測定と仮説を分けて扱います。トラック上のデバイスを原因と呼ぶことはなく（`causality.claimed` は常に false）、わからないことは名前を挙げて示します。レイテンシー、サイドチェイン、隠れたパラメータ、ゲインリダクション、デバイス内のどこに信号があったか、などです。ミキサーの変更の提案は、試してからもう一度キャプチャするための元に戻せる実験であって、dB 単位の補正を約束するものではありません。

## ワーカー

解析がホスト自身のイベントループで実行されることはありません。各ジョブは使い捨てのワーカープロセス `ableton-mcp-analysis-worker` で実行されます。

| 項目 | 制限 |
| --- | --- |
| ジョブ | 同時に 2 つ、待機 4 つ |
| 時間 | 30 秒 |
| リクエスト | 64 MiB |
| 出力 | 結果 2 MiB、エラーテキスト 16 KiB |

ワーカーはシークレットを何も引き継がず、ホストが受け取るのは JSON の結果だけです。MCP リクエストをキャンセルしたり時間切れになったりすると、ワーカーはすぐに終了させられます。

## Live からのキャプチャ

Live のスクリプトからは Live のオーディオにアクセスできないので、ブリッジは代わりに録音します。Session のクリップを 1 つ Live の Resampling 入力に向けて再生し、それを空のオーディオスロットに録音し、ファイルを測定して削除します。実際の Live で、Remote Script が `audio.capture.resampling` と 6 つの `audio.capture.*` 操作すべてを提供しているときにだけ動作します。デプロイメントポリシーでは、プレビュー、適用、緊急停止は `capture` クラスに入り（これを含むのは `full` プロファイルだけです）、`live_audio_capture_status` は読み取りです。

### プレビュー

`live_audio_capture_preview` に必要なもの：

- 開いている Set の正確な名前。Set は保存されている必要があります
- 再生する Session のクリップ 1 つと、録音先となる別の空のオーディオスロット 1 つ（別のトラック上）
- 元に戻せるように、録音先の入力ルーティングが今利用できること。Live に古い `Ext. In` が表示されているときは、先に `live_routing_*` で `No Input` を選んでください
- トランスポートが止まっていて、録音中・再生中のものがなく、どのトラックもアームされておらず、入力をモニターしているトラックがないこと
- 1 から 9 までの `durationSeconds`
- `consent: "ephemeral-analysis-and-delete"`
- `outputSafety` は省略できます

プレビューは 60 秒で期限が切れます。

### 適用

`live_audio_capture_apply` は、プレビューの予測できない確認と冪等キーを受け取ります。Remote Script は Live のメインスレッドで録音元と録音先をもう一度確認し、録音先トラックの名前を一時的にプライベートなタグ付きの名前に変え、入力を Resampling に、モニタリングをオフに、アームをオンにし、起動クオンタイズをなしにして、両方のスロットを起動します。新しいクリップを自分のものとみなすのは、Live がそれを録音中と示し、名前にタグが付いているときだけです。そのあと、トラックの名前と起動クオンタイズを元に戻します。開始を再試行することはありません。

Live 内のウォッチドッグは、最大 10 秒（要求された長さ + 3 秒）でキャプチャを止めます。停止、キャンセル、ウォッチドッグ、緊急停止、終了のどれでも、両方のスロット、トランスポート、録音を止め、再生位置、トラック名、ルーティング、アーム、モニタリングを元に戻します。そのあいだにほかの誰かが加えた変更は、上書きせずに報告します。

### 録音ファイル

ホストが受け付けるのは、保存された Set のプロジェクトフォルダー内、または User Library の `Samples/Recorded` 内にある、新しく作られた、通常の、リンクが 1 つだけの WAV だけです。最大 32 MiB、12 秒、2 チャンネルで、16・24・32 ビットの PCM または 32 ビット float のものに限ります。読み取り中は、ファイルの同一性、サイズ、時刻、SHA-256 をフェンスします。

解析のあと、リンクをたどらずに WAV とその `.asd` を開き、同一性をもう一度確認し、同じディスク上のプライベートな隔離フォルダーに移し、中身を空にして削除し、そのあとで初めて Live のクリップを削除します。続いて、メディアファイルも隔離ファイルも残っていないことを確認します。「削除」はリンクを解除したという意味で、SSD やコピーオンライトのディスクからデータが消えたことまでは約束しません。成功した結果では、Live は停止していて録音しておらず、録音先は元に戻り、スロットは空で、キャプチャの状態は `cleaned`、ファイルは何も残っていません。

結果には形式、レート、長さ、解析が含まれますが、パス、ダイジェスト、オーディオ、トークン、確認は含まれません。

キャプチャの途中で Live や Remote Script が終了すると、Remote Script は止めて戻せるものは戻しますが、自分でファイルを削除することはできません。クリップとそのファイルは、ホストかあなたが片付けられるように残されます。

### 復旧

`live_audio_capture_status` は、キャプチャの状態、録音元と録音先、再生が止まったかどうか、ファイルが利用できるかどうかを、パスや復旧トークンを出さずに示します。新しいホストプロセスからでも使えます。

状態が `cleaned` でないときは、`confirmation: "emergency-stop-and-clean"` と、ステータスに表示された同一性を渡して `live_audio_capture_emergency_stop` を呼び出します。キャプチャを止め、上と同じようにファイルを確認して削除し、そのあとで初めてクリップを削除します。パス、同一性、形式、片付けが確認できないときは、残っているものを報告し、保証できないものは何も削除しません。何かが残っているあいだは、次のキャプチャを始めないでください。

## 解析の検証

規格に沿った解析は、生成したオーディオ（第三者の録音は使いません）で、FFmpeg の独立した `ebur128` フィルターと照らし合わせて確認しています。ブリッジのテスト（`crates/ableton-mcp-server/tests/audio_standards.rs`）が、記録されているレポート [phase-8-audio-oracle.json](../evidence/phase-8-audio-oracle.json)（2026-07-27）にある、それらの信号に対する FFmpeg の結果と解析を照らし合わせます。許容誤差は、48 kHz で 0.1 LU または dB、44.1 kHz のトゥルーピークで 0.15 dBTP です。定義はあくまで公開された規格で、FFmpeg は照合のためのものです。

実際の Live では、Kumi のオプトインの受け入れテスト（`accept_live`。[テスト](TESTING.md)を参照）が再生、バウンス、聴き取りを行います。以前のキャプチャ検証ツールで記録されている最後の実行 [phase-8-audio-live.json](../evidence/phase-8-audio-live.json) は、macOS 上の Live 12.4.5b8（2026-07-27、ブリッジ 0.1.0）でのもので、現在のブリッジより前のものです。Windows での実行は記録されていません。

## 制限

- トゥルーピークは 44.1 kHz と 48 kHz のみ。
- 一般的なチャンネルラベルのみ。イマーシブやオブジェクトベースのレイアウトには対応しません。
- キャプチャには、保存された Set、WAV での録音、元に戻せるルーティングが必要です。
- Max for Live のタップ、プラグインのメーター、ファイルパスや URL、タイムストレッチ、マスタリングの評価や適合の判定はありません。
- ファイルの削除は安全な消去ではありません。あなたのユーザーとして動くプログラムはブリッジのシークレットを読むことができ、ブリッジが守る対象の外にあります。ファイルの確認は、その範囲の中で、ミスやパスのすり替えを防ぐためのものです。
